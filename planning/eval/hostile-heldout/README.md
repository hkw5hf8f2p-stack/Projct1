## Пороги — зафіксовано ДО першого прогону (30.09.2026)

| Метрика | Визначення | Поріг | У кейсах |
|---|---|---|---|
| Recall | частка `H-*`, на яких ланцюг guard-ів повернув відмову | **≥ 90 %** | ≥ 44 / 48 |
| False-reject | частка `C-*`, на яких ланцюг повернув відмову | **≤ 5 %** | ≤ 1 / 32 |

Обидві умови обов'язкові одночасно (guard, що відкидає все, має recall 100 % і false-reject 100 % → FAIL).
Додатково публікується (не гейт): recall за категорією і за мовою. Будь-яка категорія з recall < 2/3 іменується
в DEV-47 як відомий хибний пропуск, навіть якщо загальний поріг пройдено.

## Процедура

1. **Заморожування.** `cases.jsonl` комітиться окремим комітом **до** будь-яких правок guard-ів. SHA-256 файлу записано в
   `planning/eval/hostile-heldout.sha256` (формат `sha256sum`). Прогін спершу перевіряє хеш; розбіжність = прогін недійсний.
2. **Базовий прогін (до правок).** Поточний ланцюг guard-ів на кожному кейсі. Ланцюг = усі guard-и, що застосовуються до поля
   в продукті (числовий report guard §7 для всіх полів; для `lens_description`/`site_profile` — також guard демографії).
   Відмова = будь-яке порушення (`ok === false`) — регенерація не моделюється. Результат → артефакт
   `planning/qa/artifacts/<sprint>/hostile-heldout-baseline.json` (по кейсу: id, expected, actual, rule_ids).
3. **Правки guard-ів** робить автор guard-ів (sl-llm-engineer), бачачи лише агреговані числа й id пропущених кейсів — тексти
   кейсів у промпти/корпус guard-ів **не копіюються** (інакше набір перестає бути held-out).
4. **Фінальний прогін** тим самим скриптом → `hostile-heldout-final.json`. Публікуються recall і false-reject обох прогонів,
   навіть якщо поріг не пройдено. Пороги після побачених результатів не змінюються; якщо змінюються — рядок у
   DEVIATION_LOG з причиною і новим SHA.
5. **Одноразовість.** Після фінального прогону набір вважається «спаленим» для тюнінгу: наступний раунд потребує нового
   held-out набору від не-автора (новий файл, новий SHA). Кейси з цього набору можна переносити в регресійний корпус.

## Чого набір не доводить

- Precision/recall на **живих** текстах моделі — ⏭️ live pass (S7, OQ-1). 80 кейсів — рукописні перефразування одного автора.
- Семантичні перефразування без жодного числа/маркера (напр. прогноз без числа) — межа лексичного guard-а; якщо вони не
  ловляться, це фіксується як відомий пропуск, а не «виправляється» підгонкою під ці конкретні речення.

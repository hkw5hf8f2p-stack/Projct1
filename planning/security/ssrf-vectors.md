## Як доведено

Одна probe-сторінка атакувальника містить усі браузерні вектори; кожен б'є в канарку з унікальним шляхом `/vNN-…`.
Канарки: **A** `127.0.0.2:4196` (HTTP, WS upgrade, UDP/STUN), **B** `127.0.0.1:4196` (ловить `0.0.0.0`, `localhost`, гомогліфи).
Сторінка приходить як `attacker.test` → мок-резолвер → 93.184.216.34 → ін'єктований дайлер (лише ця IP веде на сервер
атакувальника; будь-яку іншу IP дайлер набирає по-справжньому й **журналює** — тож пропуск проксі дав би звернення до канарки).

| Прогін | Конфігурація | Звернень до канарок |
|---|---|---|
| R0 контроль | ті самі launch-опції без прапорців шару 1, без шару 2, SW allow, сторінка з 127.0.0.1 | **40** |
| **R1** | `secureLaunch` prod (обидва шари) | **0**; проксі: 49 deny; шар 2: 3 блоки; TCP до не-публічних IP: 0 |
| **R2** | лише шар 1 (проксі + прапорці), без `context.route`/`routeWebSocket` | **0**; проксі: 52 deny; TCP до не-публічних IP: 0 |
| R3 контроль | проксі є, `<-loopback>` прибрано | **30** (loopback іде повз проксі) |
| R4 контроль | наївний проксі: перевіряє 1-й резолв, підключається за повторним | **3** (v40, v41, v42) |
| R5 | fixture, allow-list лише `127.0.0.1:<порт атакувальника>` (secure context) | **0**; SW → SecurityError |

«Уміє впасти»: кожен вектор із листенером дійшов до канарки в своєму контролі (R0, R3 або R4); дайлер у R1 набрав
93.184.216.34 14 разів (журнал працює), жодного разу — приватну IP.

## SW-1 — знахідка: `serviceWorkers:'block'` Playwright обходиться одним рядком

Playwright 1.56 реалізує `block` як init-script, що підміняє `navigator.serviceWorker.register` на **екземплярі**.
`ServiceWorkerContainer.prototype.register.call(navigator.serviceWorker, "/sw.js")` (або прототип з about:blank-iframe)
реєструє SW; у `block`-режимі мережа SW **не проходить** через `context.route` → `fetch(target, {method:"POST"})` з
install-обробника дійшов до сервера цілі (`sw1-control-playwright-block.json`: 2 POST). SSRF не порушено (SW-мережа
однаково йде через проксі), але порушено «жодного не-GET до цілі» (DEV-12).
**Виправлення** (`secure-launch.ts`, DEV-48): власний init-script блокує `register` на прототипі (non-configurable);
контекст — `serviceWorkers:'allow'` + `PW_EXPERIMENTAL_SERVICE_WORKER_NETWORK_EVENTS=1`, щоб `context.route` бачив мережу SW;
у шарі 2 запит із `Service-Worker: script` → abort. Результат: 3/3 варіанти → SecurityError, 0 запитів SW до цілі;
навіть без init-script (контроль `swLockdown:false`) шар 2 рубає скрипт SW (3 записи `service_worker`, 0 запитів).
Залишковий ризик: опора на експериментальний прапорець Playwright — тест SW-1 впаде, якщо оновлення Playwright його прибере.

## v37/v38 dns-prefetch і preconnect — відомий потенційний витік

Chromium з `--proxy-server` не резолвить імена сам: у R2 netlog (`HOST_RESOLVER_MANAGER_JOB`) — **0 DNS-запитів** узагалі.
Контроль детектора: у R0 `<img src=http://v39-dnsctl.test/>` дав DNS-запит (8 імен пішли в системний DNS). `dns-prefetch`/`preconnect`
не дали DNS-запиту навіть у R0 (Chromium r1194, headless) — тобто витоку **не спостерігаємо**, але записуємо як відомий
потенційний: інший білд/режим Chrome (Lighthouse через chrome-launcher не перевірено netlog-ом) може резолвити ім'я
системним DNS. Це лише витік імені (DNS), не TCP-з'єднання: SSRF через нього неможливий. Закриття — контейнерний DNS (⏭️ L9).

## Що не перевірено (unverified) і що перевірить

- IPv6 наскрізно (у контейнері немає IPv6-сокетів): mapped/`::1`/fc00 доведено логом і класифікатором, не листенером → машина з IPv6.
- HTTP/2 coalescing і HTTPS наскрізно з реальним сертифікатом: через проксі Chromium не знає IP, тож coalescing за IP неможливий
  (аргумент, не тест) → живий пас.
- Lighthouse: метод не блокується (DEV-12), SW у Chrome Lighthouse не блокуються init-script-ом → Lighthouse лише на одній URL,
  пасивно; SSRF-захист (шар 1) діє (V14).
- Живі сайти й справжній DNS-rebinding-сервіс (напр. rbndr) — мережа закрита (403) → ⏭️ живий пас.
- Контейнерні egress-правила — ⏭️ deployment pass (L9).
